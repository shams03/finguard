# 06 · Domain modelling

The domain crate (`crates/domain`) is the vocabulary of the system. It has **no I/O**; everything is pure and tested without a database. The theme of this chapter: *make illegal states unrepresentable*, and where you can't, make them loud.

## 6.1 Identifiers (`ids.rs`)

🧠 **Newtype ids.** `UserId`, `AccountId`, `CardId`, `RecipientId`, `ActionId`, `TraceId`, `ConfirmationId`, `LedgerTransactionId`, plus `SessionId`, `DeviceId`. Generated by one macro (`uuid_id!`). They display as `act_<32 hex>` (readable in logs: you can tell an action id from a trace id at a glance) and parse from either the prefixed form or a bare UUID. Serde serialises them as the prefixed string.

🧠 **UUIDv7** (`Uuid::now_v7()`): time-ordered ids → better index locality than random v4, and sortable.

`IdempotencyKey(String)` validates length (≤128) and charset on construction — "parse, don't validate": once you hold an `IdempotencyKey` it is valid.

❓ *Alternatives:* plain `Uuid` everywhere (mix-ups), integer ids (guessable → enumeration attacks; also awkward across services).

💥 *Without it:* passing the wrong id type compiles. In a money system that's a latent incident.

## 6.2 Money (`money.rs`)

```rust
pub struct Money { pub amount_minor: i64, pub currency: Currency }
```

* **Never floating point.** `0.1 + 0.2 != 0.3` in binary floats. In minor units, `10 + 20 == 30`. Test: `no_float_drift`.
* **Currency is explicit.** `checked_add`/`checked_sub` return `Err(CurrencyMismatch)` for different currencies — you cannot add pesos to dollars by accident.
* **Checked arithmetic.** `checked_add` returns `Err(Overflow)` instead of wrapping. `i64::MAX + 1` is an error, not a negative number.
* **Parsing is integer-only** (`parse_major("2,000.50")` → 200050; > 2 decimals is rejected; negatives rejected).
* **Formatting:** `to_api_string()` → `PHP 2000.00`; `pretty()` → `₱2,000.00`.

❓ *Why `i64`?* Max ≈ 9.2×10¹⁸ centavos ≈ ₱92 quadrillion. Plenty. A `Decimal` library is an alternative; integers are simpler and map to `BIGINT`.

⚠️ *Honest limit:* one currency. Real systems need FX, currency-specific exponents (JPY has 0, KWD has 3), rounding rules, and "money" amounts that are not signed.

## 6.3 Typed actions (`action.rs`)

Three layers:

1. **`ActionKind`** — the allow-list of tools: `ReadBalance`, `FreezeCard`, `TransferFunds`. `FromStr` rejects everything else (`UnknownAction`). *A model's output can never name a function to execute.*
2. **`ToolSpec` registry** — per tool: `risk_class`, `required_permission`, `requires_confirmation`, `requires_jev`, `executor` (name), `argument_schema` (doc). Policy reads this table instead of hard-coding `if kind == Transfer`. A test asserts every `ActionKind` has an entry.
3. **`ActionDraft` → `ProposedAction`.** The draft may have missing fields; `draft.complete()` returns the executable `ProposedAction` or `Err(missing_fields)`.

```rust
pub enum RiskClass { ReadOnly, Reversible, MoneyMovement, HighImpact }
```
`ReadBalance → ReadOnly`, `FreezeCard → Reversible`, `TransferFunds → MoneyMovement`. Risk class drives: whether Jev is needed, the confidence threshold, confirmation, fallback behaviour.

**Fingerprint.** `ProposedAction::fingerprint(actor)` = SHA-256 of
`finguard-fp-v1\nactor=…\nkind=…\naccount=…\ncard=…\nrecipient=…\namount=…\ncurrency=…`.
Fields in a *fixed order* with a version tag — not "serialize to JSON and hash", because JSON key order isn't guaranteed. Used for confirmations and (a variant) for idempotency. Test: changing amount, actor, … changes the hash.

❓ *Why not `tool_name: String, args: serde_json::Value`?* Because the critical layers would then have to re-validate shape everywhere, and a typo would become a runtime bug. The spec says: convert to typed actions *immediately*.

💥 *Without it:* a new tool defaults to "no policy", or a stringly-typed tool name from a model reaches an executor.

## 6.4 The state machine (`state.rs`)

```
PROPOSED → VALIDATING → RISK_EVALUATING → { AWAITING_CONFIRMATION | AWAITING_CLARIFICATION | MANUAL_REVIEW | APPROVED(read-only) | BLOCKED }
AWAITING_CONFIRMATION → APPROVED → EXECUTING → EXECUTED
                      ↘ CANCELLED / EXPIRED          EXECUTING ↘ BLOCKED / FAILED
VALIDATING → BLOCKED   (hard policy)
```

`ActionStatus::allowed_next` lists legal moves; `transition(to)` returns `Err(IllegalTransition)` otherwise. Terminal states (`EXECUTED, BLOCKED, CANCELLED, FAILED, EXPIRED`) have no exits.

🧠 **State machine vs booleans.** A design with `confirmed: bool, executed: bool, cancelled: bool` has 8 combinations of which maybe 4 are meaningful; nothing stops `executed && cancelled`. An enum with explicit edges has exactly the states you meant.

In SQL the transition is `UPDATE actions SET status=$to WHERE id=$1 AND status=$from` and we check `rows_affected == 1` — optimistic concurrency: if someone else moved the action, we notice.

Notable absences (by design): `MANUAL_REVIEW → APPROVED` doesn't exist — nobody can "approve" a held action in this MVP; `AWAITING_CLARIFICATION → APPROVED` doesn't exist — a clarification must produce a *new* action which re-enters at `PROPOSED`.

## 6.5 Risk types (`risk.rs`)

* `RiskFacts` — everything we know (includes name, account number, balance). **Never sent out.**
* `RiskContext` — the minimised, allow-listed subset; this is exactly what Jev sees (chapter 08).
* `RiskAssessment` — vendor-neutral result: `intent_alignment`, `behavioral_anomaly`, `recipient_risk`, `context_sufficient`, `overall_confidence`, `provider_metadata` (model, **client-measured** latency, question-set version, tokens, credits) and the raw questions/answers for audit.
* Traits: `DecisionProvider`, with error enum `DecisionProviderError`.

Same pattern for `IntentParser` (`intent.rs`) and `EscalationAnalyzer` (`escalation.rs`). **All vendor JSON stops at the adapter crates**; the rest of the code sees domain types only.

## 6.6 Decisions as data (`decision.rs`)

`HardPolicyReport { checks: Vec<HardCheck>, result }`, `PolicyDecision { Execute | RequireConfirmation | AskForClarification{question} | ManualReview | Block{reason} }`, `BlockReason`. They are plain, serialisable data → stored in the DB, returned by the API, rendered by the UI, replayed in tests.

## 6.7 Redaction (`redact.rs`)

`Secret<T>` (Debug prints `[REDACTED]`), `scrub_text` (emails, long digit runs, tokens, control chars, length cap), `redact_database_url`, `redact_known`. Pure, tested.

## What breaks if you remove it (mutation list)

| Remove / change | Expect this test to fail |
|---|---|
| Add `Executed → Executing` edge | `terminal_states_have_no_exits_and_money_cannot_skip_confirmation` |
| Drop currency check in `checked_add` | `arithmetic_is_checked` / compile of callers |
| Fingerprint ignores amount | `fingerprint_is_deterministic_and_binds_every_field` |
| `ActionKind::from_str` accepts anything | `unknown_tool_is_rejected` |
| Remove an entry from `REGISTRY` | `registry_covers_every_kind_and_transfers_need_confirmation` |
